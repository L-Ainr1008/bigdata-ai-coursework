1. 概念速览

一句话定义：Skill 是存放在文件系统里的一个文件夹，它把"把某一类任务做好"所需的指令、脚本和参考资料打包在一起；智能体平时只在上下文里保留它的名字和简介，判断当前任务对得上时才把正文读进来，需要更细的细节时再往下翻[1][2]。

它不是什么

  • 不是一段一次性的提示词。提示词说完就散、下次要重新敲；Skill 是落在磁盘上的文件，会被反复"发现—加载"，同一次安装可以服务无数次对话[2]。
  • 不是模型微调（Fine-tuning）。它一个模型权重都不改，只是在恰当的时机往上下文里塞恰当的指令。
  • 不是工具（Tool）或插件。工具回答的是"我能按什么动作"，Skill 回答的是"这件事该怎么做"；两者不在同一层——不过 Skill 里面可以带着脚本，让模型当成工具直接跑[2]。
  • 不是智能体（Agent）本身。智能体是干活的角色，Skill 是它能去翻的那本手册。没有智能体，手册没人读；没有手册，智能体每次都得靠猜[3]。

一句话个人理解

我觉得 Skill 最像给新同事准备的一本操作手册：你不用每次开工前口头交代一遍"表格要用这个字体、数据要先去重、报告要分三段"，而是把这些要求写成文档放进抽屉，他自己会在合适的时候翻开照做。

但这个类比有三个地方会失真，必须说清楚：

  • 手册不会自己动手，Skill 也不保证模型一定照做。加载不等于服从。模型读完 Skill 之后，仍然可能按自己的理解发挥，或者压根没触发这本"手册"。
  • 人类新同事看手册是"读一遍就记住了"，模型不是。模型没有跨会话的记忆，每次对话都要重新走一遍"发现—加载"的流程，上下文一清空就全忘了。这是 Skill 存在的根本原因之一，也是它和"培训一个人"最大的差别。
  • 手册会过期，Skill 也会，而且更隐蔽。公司流程变了，旧手册不会自己报错，只会让你在新流程下做出旧格式的东西。Skill 维护成本就出在这里。

2. 学习目标

  1. 能自己说清 Skill 是什么、解决什么问题，并且能举出至少一个"不适合做成 Skill"的反例——而不是只会背定义。
  2. 能看懂并写得出一个最小可用的 SKILL.md：知道 name 和 description 是必需的，知道正文该写什么、什么该拆到附属文件里去[2]。
  3. 能解释"渐进式披露"（progressive disclosure）为什么要分三层，以及每一层分别在什么时候进入上下文、代价是什么[2]。
  4. 能把 Skill、提示词、Tool/MCP、Agent 四者的分工讲明白，并说明它们怎么配合，而不是互相替代[1][2][3][4]。

3. 核心问题

  1. 既然上下文窗口越来越大，为什么还要费劲分层加载？把全部指令一次性塞进去不是更简单吗？（答案见第 4 节与第 7 节第 1 题）
  2. description 到底该写多长？写短了模型匹配不到、技能形同虚设；写长了它又常驻在上下文里占地方。这个取舍的边界在哪？（答案见第 4 节要素二、第 6 节第 4 条）
  3. 什么时候该写 Skill，什么时候该写成脚本/工具？如果一件事用 Python 脚本能稳定跑通，还需要 Skill 吗？（答案见第 4 节要素五、第 6 节边界小节）

4. 核心机制

Skill 的运行机制可以拆成五个要素。它们的关系不是并列的，而是一条有先后、有依赖的链：要素二是要素三的入场券，要素三是要素四的目录，要素五则挂在正文下面按需调用。

要素一：载体 —— Skill 是一个目录，SKILL.md 是它的入口

最简形态下，一个 Skill 就是一个文件夹，里面有一个 SKILL.md；复杂一点的会带上参考文档、模板和脚本[2]。

为什么需要它：因为"文件夹"意味着它可以被文件系统管理——能被列出来、能被cd进去、能按文件名读取。Skill 的按需加载能力，本质上是借了"文件可以只读其中一部分"这个古老的特性。如果 Skill 只是一个字符串常量，就只能整段进上下文，没有"按需"可言。

要素二：第一层 —— YAML 元数据（name + description）

文件开头必须是 YAML frontmatter，其中 name 和 description 是必需的。智能体在启动时，会把每一个已安装技能的 name 和 description 预加载进系统提示——注意是"全部技能、但只有这两项"[2]。

为什么需要它：这一层的作用是让模型"不读全书也能判断该不该读"。它必须常驻，否则模型无从知道自己手上有这个技能；它也必须极短，否则装 50 个技能光目录就把上下文吃掉了。这个"既要常驻、又要极短"的矛盾，是理解 Skill 设计的关键。

一个容易被忽略的推论：正因为 description 常驻，你的技能数量会线性地侵蚀上下文预算。description 写 50 字还是 500 字，在装了 30 个技能时是几十倍的区别。这也是官方强调"只在需要时加载"的原因[1][2]。

要素三：第二层 —— SKILL.md 正文

当模型判断某个技能与当前任务相关时，才会把完整的 SKILL.md 读进上下文[2]。正文写的是"这件事具体怎么做"：步骤、检查清单、输入输出约定、反例。

为什么需要它：它是"判断相关"和"动手执行"之间的桥。没有这一层，模型只有一句简介，知道"有本手册"却不知道手册里写了什么。

要素四：第三层及更高 —— 附属文件

正文里可以按文件名引用更多文件（如 reference.md、forms.md），这些细节只在特定子场景下才被需要，模型可以选择性地去导航和发现[2]。

为什么需要它：这是"上下文量近乎无限"的技术来源。既然不必一次读完，一个技能包里能装多少内容就不再受上下文窗口限制——官方的说法是 effectively unbounded[2]。这一步把 Skill 从"长一点的提示词"抬升成了"一个可伸缩的知识库"。

要素五：可执行脚本（可选，但很关键）

Skill 里可以放代码，让模型直接运行而不必把脚本或数据读进上下文。而且因为代码是确定性的，同样的输入会得到同样的输出，这一点是逐 token 生成做不到的[2]。官方的例子是：用 token 生成去排序一个列表，远比直接跑一个排序算法昂贵[2]。

为什么需要它：它划出了 Skill 的能力边界——能用代码确定性解决的，就别让模型去"生成"。逢春有 Python 基础，这一点特别值得记：Skill 不是让模型变聪明，而是让它少干不该它干的活。

5. 应用场景

选一个逢春自己真实会遇到的、可复现的场景：课程要求"学透一个概念，产出一份可复查的学习资料"。这个任务他这学期要做不止一次——前面已经做过 Agent 和大模型的上下文，这次是 Skill，后面还会有 RAG、向量数据库等等[3]。

6. 易混淆点与边界

6.1 五条易混淆点

条目常见误解正确说法为什么会错
① Skill vs 提示词[2] "Skill 就是存起来的长提示词，本质一样。" 提示词是一次性全部进入上下文的文本；Skill 是文件，只有元数据常驻，正文和附属文件按需分层读取。两者在"占用多少上下文、什么时候占用"上根本不同。 因为最终效果看起来一样——都是"给模型一些文字，它照着做"。人容易从"结果相似"倒推"本质相同"，忽略了加载时机和代价的差异。而这个差异恰恰是 Skill 的全部价值所在。
② Skill vs 工具 / MCP[2][4][5] "Skill 和 MCP 服务器是一回事，都是给模型扩展能力。" 两者是互补而非替代。MCP 解决"能连上哪些外部系统"[4]；Skill 解决"连上之后，这一整套活该怎么干"。而且 Skill 里可以打包脚本当工具跑[2]，所以 Skill 是包住工具的一层，不是和它并列的一层。 因为两者装上都"让模型变强了"，从使用者视角看不出区别。加上 Skill 可以包含脚本，更容易让人以为"Skill = 工具"。区别在于：工具是能力（能不能做），Skill 是程序性知识（该怎么做）。
③ Skill vs Agent[3] "一个装了很多 Skill 的 Agent 就等于一个更强的 Agent，两者是包含关系。" Agent 的定义特征是由 LLM 动态决定自己的流程与工具使用、并保有对任务完成方式的控制权[3]。Skill 不参与这个决策，它只是决策过程中可被查阅的资料。装了 Skill 的 Agent 仍是 Agent，只是手边多了手册。 因为 Skill 确实改变了 Agent 的行为表现，容易把"改变了输出"当成"改变了架构"。建议对照仓库里已有的 agent.html 一起看：Agent 讲的是"谁在做决定"，Skill 讲的是"决定时手边有什么资料"。
④ description 的写法[2] "description 写得越详细越好，这样模型更容易匹配上。" description 常驻 system prompt，而且是每个已安装技能各占一份[2]。它是"检索用的索引"，不是"使用说明"。索引的价值在于用最少的字把对的请求钩住、把错的请求挡掉，堆细节反而抬高成本、稀释信号。 这是把"信息量"当成了"有效性"。人写文档习惯"多多益善"，但常驻内容的计价方式是"每个 token × 技能数 × 每轮对话"。正确的写法（可对照 concept-study-generator）：正向触发词 + 反向排除条件，其余全交给正文。
⑤ "加载了" ≠ "会照做"[2] "只要 Skill 被加载了，输出就一定会符合里面的规范。" Skill 提供的是指令，不是约束。模型读完后仍可能不照做、做一半、或理解偏。真正要"保证"的部分，应该写成可执行脚本（确定性）或交付前自检清单（靠流程兜底），而不是指望模型自觉遵守文字约定[2]。 这是最普遍的一类错误：把"能力"当成"必然行为"。看到模型能做到，就以为它每次都会做到。这也解释了为什么 concept-study-generator 要专门设第七节自检清单——它是对"模型不一定照做"这件事的显式防御。

6.2 使用边界

什么不适合做成 Skill：

场景为什么不适合 / 该怎么做
需要实时数据的任务
（今日股价、最新新闻）		 Skill 是静态文件，写出来那一刻就冻结了。它擅长存"怎么查、怎么整理"，不擅长存"查到的结果"[2]。实时数据要靠工具/检索去取，Skill 只管取回来之后怎么加工。
能用代码确定性解决的重复劳动 比如"批量核验 5 个链接是否返回 200"。这类事该写成脚本放进 Skill（要素五），而不是写成一大段让模型模仿的操作说明[2]。让模型逐 token 生成 curl 的结果，既贵又不可靠。
只用一次的任务 Skill 的收益来自复用。写一份要花时间，还要维护，只用一次就是纯亏。直接写提示词即可。
没有可核查来源支撑的内部概念 以 concept-study-generator 自己的规定为例：概念本身不存在可核查的公开来源时，会直接触发来源校验失败[2]。这时该改方式，不要硬套。
纯知识性、模型本来就知道的内容 没必要教模型"什么是 Python 的 for 循环"。Skill 的价值在于沉淀模型不知道的、你专属的流程与标准。

6.3 维护成本

  • Skill 会腐化，而且不会报错。流程变了、工具接口改了，旧 Skill 不会抛异常，只会安静地引导模型按过时的方式做事。concept-study-generator 里的默认路径、章节结构一旦改动，所有历史产出就与现行规范不一致了。
  • 技能越多，常驻成本越高。每加一个 Skill，就多一份 description 永久占用 system prompt。这是随技能数量线性增长的固定开销，装到几十个时必须重新审视每一条 description 的长度。
  • 改动的波及面不透明。改一个 SKILL.md，所有依赖它的历史任务产出都不会自动更新，也没有机制告诉你"哪些旧结果已经过时了"。

6.4 技能之间冲突怎么办

官方把"可组合（Composable）"列为 Skill 的四大特性之一，并称 Claude 会自动判断需要哪些技能并协调它们的使用[1]。但作为使用者，我倾向于不把这件事当成理所当然——结合 6.1 的第 ⑤ 条（加载 ≠ 照做）来看，"自动协调"本身也是模型的一次判断，同样可能出错。可操作的做法是：

  1. 先在 description 里划清地盘。这是唯一常驻、也是唯一能在"加载之前"起作用的闸门。像 concept-study-generator 那样把"不适用于"明写进去，是成本最低的防冲突手段。
  2. 重叠区域写清优先级。两个技能都能沾边的任务，在各自正文里指明"若同时涉及 A 与 B，以 A 为准"，别让模型自己猜。
  3. 能合并就合并。两个技能如果 80% 的场景都同时触发，说明拆错了粒度，合成一个、用第三层附属文件做分支，比留着它们互相打架更省事。
  4. 靠输出自检兜底。把"检查是否误用了不该用的技能"写进自检清单——这又是 concept-study-generator 第七节那种思路的延伸。

7. 自测题

陷阱判断1. 判断题：为了让模型充分了解一个技能，Skill 的正文和附属参考文件会在对话开始时就全部加载进上下文，这样模型才能随时调用其中的细节。

查看答案与解析

✗ 错误。这句话听起来很"有道理"（信息越全越好），但它描述的恰恰是 Skill 要避免的做法。

正确机制是：启动时只有全部技能的 name + description 被预加载进 system prompt（第一层）；模型判断任务相关后，才把 SKILL.md 正文读进上下文（第二层）；附属的 reference.md 一类文件属于第三层及更高，由模型按需去导航发现[2]。

为什么这是陷阱：它把"传统长提示词的做法"伪装成了"Skill 的做法"。如果真的全部预加载，就退化成了普通长提示词，装几个技能上下文就爆了——Skill 的整个设计（官方称之为渐进式披露）就是为了解决这个[2]。记住这句判断标准：凡是"一次性全塞进上下文"的描述，都不是 Skill。

选择2. 一个技能包里有一份"表单填写说明"，只在极少数需要填表的子任务里才用得上。按渐进式披露的设计原则，它应该放在哪里？

A. 写进 description，让模型一眼就看到
B. 写在 SKILL.md 正文里
C. 拆成独立文件（如 forms.md），由正文引用
D. 不放进技能包，每次临时告诉模型

查看答案与解析

✓ C。这正是官方示例中的做法：把表单填写说明移到单独文件，让技能正文保持精简，相信模型只在真正填表时才会去读它[2]。

  • A 错：description 常驻 system prompt，把低频细节放进去是永久占用上下文，最浪费的位置。
  • B 错：正文一旦命中就会整体读入，低频内容混进去会拖累每一次命中。
  • D 错：那就退回"每次手动交代"，Skill 的复用价值没了。

判断口诀：越低频、越细、越只在特定子场景用到的内容，就该放越深的层。

选择3. 逢春想让模型每次都把一组 20 个来源链接核验一遍返回码。他应该？

A. 在 Skill 正文里详细写出 curl 命令的格式，让模型照着生成
B. 写一个 Python 脚本放进技能包，让模型直接运行它
C. 在 description 里强调"必须核验来源"
D. 每次对话时手动提醒模型

查看答案与解析

✓ B。技能里的代码可以被直接运行，既不必把脚本也不必把数据读进上下文；而且代码是确定性的，同一个输入永远得到同样的输出，这一点逐 token 生成本质上做不到[2]。

A 是很多人的第一直觉，但它让模型去"生成"本该"计算"的结果——既贵又可能出错。C 只解决了"要不要做"，没解决"怎么做才可靠"。D 完全放弃了复用。

这道题对应核心问题 3：能用代码确定性解决的，就不要让模型生成。逢春有 Python 基础，这正是他在 Skill 里最能发挥优势的地方。

判断4. 判断题：只要写好了 SKILL.md 并且模型成功加载了它，产出的结果就一定符合里面规定的格式。

查看答案与解析

✗ 错误。Skill 提供的是指令而非约束。加载不等于服从，模型读完仍可能不照做、只做一半，或者压根没触发这个技能。

想要提高可靠性，有三个层次：能用脚本确定的就写成脚本（最可靠）；把验收标准写成交付前的自检清单，让模型逐条打勾（靠流程兜底，concept-study-generator 第七节就是这个思路）；把边界条件写进正文（最弱，依赖模型自觉遵守）。

这题考的是 6.1 第 ⑤ 条：不要把"模型有能力做到"当成"模型每次都会做到"。

简答5. 结合仓库里已有的 agent.html（智能体）和 llm-context.html（上下文窗口）两份资料，说明：Skill 的"分层加载"设计，到底在优化什么资源？如果上下文窗口是无限的，Skill 还有必要存在吗？

查看答案与解析

第一问：优化的是上下文窗口这一稀缺资源（可对照 llm-context.html 复习）。三个具体表现：① 平时只让两行元数据常驻，把常驻成本压到最低；② 正文命中才读，避免无关内容占位；③ 第三层按需再读，使得单个技能能装的内容量"近乎无限"[2]。此外还有个隐性收益——上下文越干净，模型注意力越集中，这不只是"省钱"问题。

第二问（开放题，言之成理即可）：我的看法是仍然有必要，但价值重心会转移。

  • 仍然成立的价值：复用与一致性（不用每次重述要求）、经验固化（教训写进流程而不靠记性）、可移植（同一份技能跨应用复用[1]）、以及"把确定性的活交给脚本"带来的可靠性[2]。这些都和上下文大小无关。
  • 会消失的价值：分层加载带来的 token 与注意力节省。如果上下文无限，"分三层"就纯粹是多余的复杂度，直接全塞进去更简单。

换句话说，分层是手段不是目的——它是"上下文稀缺"这个约束下的最优解。约束变了，手段就该跟着变。能看出这一点，说明理解了机制背后的为什么，而不只是记住了"有三层"。
