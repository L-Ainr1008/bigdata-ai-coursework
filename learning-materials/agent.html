Agent（智能体）：从"会回答问题"到"会自己把事办完"

课程：《大数据与人工智能》　｜　学习者：逢春　｜　资料类型：概念学习单（自学 + 作业提交）
阅读前基础：会写 Python、没系统学过 AI 理论　｜　预计阅读用时：20~30 分钟

1概念速览

一句话定义 Agent 是一个以大模型做决策核心、能围绕一个目标自己规划步骤、调用外部工具、并把工具返回的结果当作新信息继续往下推进，直到任务完成或触发停止条件的系统。[1]
它不是什么（这几条同样重要）
  • 不是"更聪明的聊天机器人"。聊天机器人一轮问答就结束；Agent 的价值在于多轮自我推进——上一轮的结果会改变下一轮的动作。
  • 不是"某款具体产品"。Agent 是一种系统组织方式，不是一个软件名字，也不是某个框架专属。
  • 不等于"自动化工作流"。固定流程（先 A 再 B 再 C）是人把路径写死；Agent 是模型在运行时临场决定路径。[1]
  • 不等于"有自主意识"。它没有任何意愿、目标感或自我认知，"目标"完全来自人类的指令和系统设计。
  • 不是"效果一定更好的方案"。能用固定流程稳定解决的事，套上 Agent 往往只是增加了不确定性和成本。[1]
一句话个人理解（我自己的话） 对我来说，Agent 就是把"大模型"从一个只会动嘴的顾问，改装成一个手上长出了工具的实习生：顾问只告诉你"你可以先查资料再整理"，实习生则会真的去查、查完发现不对再换关键词、凑齐了才把表格交给你——差别不在脑子的聪明程度，而在有没有"动手 — 看结果 — 改主意"这个闭环。

2学习目标

读完这份资料，我应该能够做到这四件事：

  1. 说清楚 Agent 和普通 LLM 问答的分界线，并且能用自己的话解释"多步闭环"到底多了哪一步。
  2. 画出 Agent 的基本结构，说出它的 5 个组成要素分别负责什么，指出其中哪一个是真正干活的（提示：不是模型）。
  3. 判断一个需求该不该用 Agent，能举出"用固定流程更好"的反例，而不是凡是任务就上 Agent。[1]
  4. 写出一个最小 Agent 循环的代码骨架（Python），说清楚每一步为什么这么写，尤其是"护栏"那几行。

3核心问题

下面三个问题驱动整份资料，读完应该都能回答：

  1. "模型调用工具"这件事，到底是模型在调用，还是我们的程序在调用？如果不是模型亲自执行，那"会用工具"这个说法还剩多少含金量？（见第 4、6 节）[3]
  2. 既然 Agent 能自己规划，为什么工程实践中反而强调"能不用就别用"？自由度的代价是什么？（见第 6 节）[1]
  3. 一个 Agent 跑到第 50 步还没停，是谁的锅？系统会用什么机制防止它无限循环或捅娄子？（见第 4 节要素 5）

4核心机制

Agent 不是某个神秘模块，而是五个部分拼起来的一个循环。我按"谁负责什么"拆开记：

要素 1：大脑 —— LLM 决策器

它唯一的工作是：看着当前的所有信息，判断"下一步做什么"。输出通常不是一个答案，而是一个决定——要么继续调工具，要么给出最终答复。注意它不直接干活，就像指挥官不下场挖战壕。

要素 2：工具箱 —— Tools

工具就是一些普通函数或 API：搜索、读文件、查数据库、发请求、执行代码……模型负责"决定调哪个、传什么参数"，真正执行的是我们自己写的程序。这一点是整个概念里最容易理解错的地方（详见第 6 节）。研究工作中，让模型学会产生可被机器执行的调用动作，正是 ReAct 与 Toolformer 这两篇论文关注的核心。[2][3]

要素 3：记忆与状态

  • 短期记忆（工作记忆）：这一轮任务里已经发生的"思考—动作—结果"序列，也就是轨迹（trajectory）。没有它，模型每一步都像失忆，会反复做同一件事。
  • 长期记忆：跨任务要留存的东西，比如用户偏好、历史结论、知识库检索结果。

把外部系统（文件、数据库、知识库）接进来的这层"接线标准"，业界正在形成开放协议，例如 Model Context Protocol（MCP）——它规定的是怎么接，不是 Agent 本身。[5]

要素 4：循环 —— 思考 → 动作 → 观察

这是 Agent 的心跳。ReAct 这篇论文把"推理"和"行动"显式地交替起来：先想一步（Thought），再做一个动作（Action），然后接收环境反馈（Observation），再想一步……[2] 拆开看每一步都很笨，但串起来就产生了"遇到障碍会改道"的能力。

要素 5：停止条件与护栏

没有护栏的 Agent 是一个可能永远跑下去的循环。必须显式设计：最大步数上限、预算/时间上限、失败重试上限，以及高危动作（删除、付款、发消息）必须先过人工确认。[4]

流程图

① 目标用户给出任务与可用工具清单
→
② 大脑 LLM思考：当前缺什么？下一步做什么？
→
③ 动作输出"调哪个工具 + 传什么参数"
→
④ 执行我们的代码真正调用工具
→
⑤ 观察把结果作为新信息追加进上下文
⟲　观察结果回流到 ②，进入下一轮；直到大脑判断"目标已达成"，或触发步数 / 预算 / 人工叫停等护栏 → 输出最终结果 
        ┌──────────────────────────────────────────────┐
        │                                              │
        ▼                                              │
   [用户目标] → [大脑: Thought] → [Action: 调工具] → [执行] → [Observation]
                      │                                        │
                      │ 判断"信息够了"                          └──── 回流 ──┘
                      ▼
                 [最终答案]  ←──── 护栏触发时在此强制中断

最小代码骨架（Python 伪代码，我按上面的要素自己写的）

tools = {
    "search_paper": search_paper,   # 输入关键词，返回论文列表
    "read_pdf":     read_pdf,       # 输入路径，返回正文文本
}

messages = [
    {"role": "system", "content": "你是一个研究助理，信息不足时必须先查再答。"},
    {"role": "user",   "content": "整理这 10 篇论文的核心结论"},
]

for step in range(MAX_STEPS):                 # 护栏 1：步数上限，防止无限循环
    reply = llm(messages, tools=tools)        # 要素 1：大脑只决定"下一步做什么"

    if reply.type == "final_answer":          # 要素 5：模型自己判断可以收工
        print(reply.content)
        break

    if reply.tool_name in DANGEROUS:          # 要素 5：高危动作必须人工批准
        raise PermissionError("高危操作需要人工确认：" + reply.tool_name)

    # 要素 2：真正执行工具的是我们的代码，不是模型
    result = tools[reply.tool_name](**reply.args)

    # 要素 3+4：把 Observation 追加回上下文，形成下一轮的输入
    messages.append({"role": "tool", "content": result})
else:
    # for-else：循环没被 break 打断，说明跑满了步数还没完成
    print("已超过最大步数，任务未完成，请人工介入")

这段代码里最值得记的一行是 result = tools[...](**reply.args)：模型只产出了一个"想调用什么"的文本结构，动手的是我们自己的 Python 函数。

5应用场景

不讲虚的"智能客服"，挑一个我自己真会遇到的场景：

场景：把 10 篇英文课程论文的核心结论整理成一张中文对比表

环节具体内容
输入 一句自然语言目标："把 downloads 目录里这 10 篇 PDF 的方法、数据集、主要结论整理成一张中文表格，缺的信息标注'未提及'。"加上工具清单：list_files、read_pdf、translate、write_table。
处理 ① 列目录，发现只有 9 个 PDF → 不是硬着头皮做，而是先报告"少一篇"；
② 逐篇读取，第 3 篇是扫描件读不出文字 → 换策略，标记"需人工处理"后跳过，继续下一篇；
③ 读到第 7 篇发现它和第 2 篇是同一方法的不同版本 → 主动比较差异而不是各写一行；
④ 发现某篇论文没写数据集规模 → 回去重读实验章节，仍找不到就填"未提及"（而不是编一个）；
⑤ 凑齐后调用 write_table 输出，并附上"3 处需要你复核"的清单。
输出 一张 10 行的中文对比表（含"未提及"标记）+ 一份不确定项清单 + 一句"第 3 篇是扫描件，需要你手动补"。
如果不用 Agent，会怎样？
  • 纯聊天机器人：它根本没读过我的 PDF，要么让我自己把全文贴进去（贴到第 3 篇就超上下文了），要么凭领域印象编一份"看起来很对"的表——这是最危险的结果，因为它编得很像真的。
  • 写死的脚本：我能写一个"遍历 PDF → 抽取 → 翻译 → 输出"的脚本，但它遇到扫描件会直接抛异常，遇到缺字段会填 None，遇到第 10 个文件不存在会崩。每个意外都要我提前想到并写 if-else，而 Agent 是遇到意外时临场绕路。
  • 结论：这类任务的特点是步骤数不确定、异常情况多、需要边看边改主意——正好落在 Agent 的舒适区。
反过来说，什么时候不该用？ 如果只是"把 10 个 PDF 的文件名改成统一格式"，写个 for 循环 20 行搞定、跑一万次结果都一样。套上 Agent 等于花 10 倍成本去换一个"可能改错文件名"的风险。[1]

6易混淆点与边界

常见误解 正确说法 为什么会错（把人带沟里的原因）
① "Agent 就是更聪明的 ChatGPT。" 两者的脑子可能是同一个模型，区别在于有没有闭环：Agent 会把动作的结果拿回来继续决策，而一次性问答不会。[1] 因为它们对话时"长得一样"，都是从输入框到文字输出，外观上看不出差别。但系统的控制流完全不同：一个是单箭头，一个是带回路的环。
② "模型调用了搜索工具，所以它能上网。" 模型只是生成了一段符合格式的文本（"我要调 search，参数是 xxx"），真正发请求的是我们的程序；模型从头到尾没接触过网络，它看到的是我们把结果抄回给它的文字。[2][3] 因为在代码层面我们会写 llm(messages, tools=tools)，看起来像把工具"递给"了模型。这个 API 写法掩盖了中间那步"程序代执行"。
③ "自由度越高越好，什么都该让 Agent 自己规划。" 工程实践里明确的建议是从最简单的方案开始，能确定性地解决就别加自主性；每多一分自由度，就多一分不可复现、难调试和出错放大的风险。[1][4] 因为演示视频里 Agent 自主解决问题特别酷，容易给人"越自主越强"的印象。但课程作业和真实生产要的是稳定复现，不是偶尔惊艳。
④ "Agent 会自己停下来，因为它是智能的。" 停止条件必须由系统设计者显式写出来：步数上限、预算上限、超时、人工确认关卡。模型自己判断"该收工了"只是其中一条路径，不能只依赖它。[4] 因为大多数时候它确实停了，让人以为这是模型的"常识"。实际上一旦某步出错、观察结果始终"不够"，它就会一直在环里绕圈烧钱。
⑤ "MCP 是一个 Agent 开发框架。" MCP 是协议层，规定 Agent / 应用怎么以统一方式连接外部数据源和工具；它不负责规划、不负责推理，跟"Agent 框架"不是一个层次的东西。[5] 因为它几乎总是和 Agent 讨论一起出现，还经常被说成"给 Agent 接工具用的"，听着就像框架。类比：它是USB 接口标准，不是电脑本身。
类比：Agent ≈ 带工具箱的实习生 大脑 = 实习生的判断力；工具 = 他手上的搜索引擎、Excel、命令行；记忆 = 他做过的记录本；循环 = 他"查一下、对一下、改一下"的工作节奏；护栏 = 主管给他定的"超过 2 小时必须来问我""涉及付款必须请示"。

这个类比的边界在哪（很重要）：实习生有责任心和自我意识——他会因为"怕做错"而主动谨慎，会记得上次被批评过。Agent 完全没有这些，它的"谨慎"只是提示词里的一行字，随时可能被某一步的输出冲掉；它也不会真的"记得"上一次，除非你把上次的内容重新放进上下文。凡是涉及后果不可逆的动作，类比失效，必须回到"这是个没有主观意识的循环程序"来理解。

7自测题

建议先写在纸上再展开答案——直接看答案等于没测。

第 1 题 · 判断看起来对其实错

"既然工具调用的结果会返回给模型，说明模型具备访问外部世界的能力，只是需要工具作为中介。"

查看答案与解析

判断：错误。

前半句对，结论错。结果确实会返回给模型，但返回的形式是纯文本，而且中间隔着一层我们自己的程序。模型从头到尾只做了一件事：根据上下文生成下一段文本（其中一段恰好长成"工具调用请求"的样子）。真正访问外部世界的是我们的 Python 代码。

为什么这话诱人：它把"信息最终到达了模型"偷换成了"模型具有访问能力"。按这个说法，我给你发一条短信告诉你今天下雨，就等于你具备了气象观测能力——显然不成立。[2][3]

第 2 题 · 选择

下列哪一项最能作为"这个需求应该用 Agent、而不是固定脚本"的判断依据？

A. 任务需要调用 3 个以上的工具
B. 任务的输出是自然语言
C. 任务的执行路径无法事先穷举，需要根据中间结果临时决定下一步
D. 任务涉及大模型

查看答案与解析

答案：C。

A 错：工具多不代表路径不确定，写死顺序照样能跑十几个工具。B 错：输出是不是自然语言跟架构无关。D 错：涉及模型只是必要条件，用了模型不等于要用 Agent。
判断的真正分水岭是路径的不确定性——如果你能在写代码时就把完整流程图画出来，那它是工作流；画不出来、必须"看一步走一步"，才轮到 Agent。[1]

第 3 题 · 简答

请说出 Agent 的 5 个组成要素，并指出其中"真正执行动作"的是哪一个。要求每个要素一句话，不能只报名字。

查看答案与解析
  1. 大脑（LLM 决策器）：看当前状态，决定下一步是调工具还是收工。
  2. 工具箱：可供调用的函数/API，由我们的程序真正执行。
  3. 记忆与状态：短期保存本轮轨迹，长期保存跨任务信息。
  4. 循环：Thought → Action → Observation 的交替推进。[2]
  5. 停止条件与护栏：步数/预算上限与人工确认关卡。

真正执行动作的是"工具箱"那一步，也就是我们自己写的代码，不是模型。答成"模型"或"Agent 自己"是最常见的失分点。

第 4 题 · 代码阅读

看第 4 节代码骨架里的 for step in range(MAX_STEPS): ... else: print("请人工介入")。请回答：这个 else 在什么情况下会执行？如果把 MAX_STEPS 设成一个很大的数（比如 100000），会带来什么具体问题？

查看答案与解析

触发时机：Python 的 for-else 中，else 只在循环没有被 break 打断、正常跑完时才执行。在这里意味着"跑满了步数，模型始终没给出最终答案"。

设成 100000 的问题：护栏等于形同虚设。一旦某一步的观察结果让它觉得"信息还不够"，它就会持续绕圈，具体后果是：① 费用按 token 累计，可能一夜烧掉可观金额；② 上下文不断变长，最终超出模型窗口而崩溃，或者因为太长导致注意力被稀释、越跑越糊涂；③ 如果工具有副作用（反复写入文件、重复下单），错误会被放大 100000 倍；④ 出问题后轨迹极长，根本没法定位是哪一步开始跑偏的。合理的做法是设一个小到让人肉疼但够用的上限（比如 10~30 步），并在超限后把轨迹存下来人工复盘。[4]

第 5 题 · 判断与纠错

"我给 Agent 接上了 MCP，所以它现在具备了自主规划能力。"

查看答案与解析

判断：错误。MCP 解决的是连接问题——用统一协议把数据源和工具接进来，相当于给电脑统一了 USB 口。它不提供规划、推理、循环控制，这些仍然由大模型和我们的循环代码负责。

正确表述："我给 Agent 接上了 MCP，所以它现在可以用统一方式接入更多工具和数据源；它的规划能力仍来自模型本身。"[5]

9我的疑问

  1. Agent 的"规划"和模型的"推理"边界到底在哪？我现在的理解是：规划发生在一次模型输出的"想法"里，而步与步之间的推进是靠外部循环代码。那如果一个 Agent 完全没有外部循环，只是模型在单次输出里写一大段"计划 + 逐步执行"，它还算 Agent 吗？还是说这只是"长得像规划的文本"？这个我没想通。
  2. 步数上限该按什么定？我理解要设小一点，但"小到肉疼但够用"是我自己的感觉，有没有更靠谱的估计方法？比如能不能按任务类型给个经验区间？
  3. 多个 Agent 协作时，错误会怎么传播？单个 Agent 跑偏我还能看轨迹找原因，如果是 A 的输出喂给 B、B 再喂给 C，是不是每一步的偏差会叠加放大？业界一般怎么观测和控制这种情况？
  4. 长期记忆到底该存什么？直觉上"什么都存"肯定不行（会污染上下文、检索出不相干的东西），但"存多少算合适"我没有判断标准，也不知道业界有没有比较公认的做法。
