概念学习资料：大模型的上下文（Context / 上下文窗口）

课程：《大数据与人工智能》  |  学习者：逢春  |  基础：有 Python 基础，未系统学过 AI 理论
资料类型：单文件自包含 HTML  |  文中 [1] 等上标对应第 8 节「资料来源」

1概念速览

一句话定义

上下文窗口，是模型在生成下一个 token 时，能够"回头看见"的那段 token 序列的长度上限；它是模型的一次性工作记忆，而不是它的长期知识。

它不是什么（这三条是后面所有内容的地基）
  • 它不是模型的"记忆"。上下文随会话结束而消失。下次新开一个对话，哪怕同一个模型，它对上次聊过什么一无所知——除非你把上次的内容重新写进这次的输入里。
  • 它不是模型的"知识"。模型的知识来自训练语料，被固化在参数里；上下文里塞进去的资料只是这次"临时借给它看"，看完就走，不会让它真的学会。
  • 它不是越大就越好的性能指标。"装得下"和"用得好"是两件事。窗口再大，模型对窗口内不同位置信息的利用程度也并不均匀，塞满甚至会拖累表现 [2][5]。
一句话个人理解（逢春）

我把它理解成一块"每次提问前要重新写满的白板"：模型是失忆的，它每一次作答都只看眼前这块白板上现在写着什么，所以我必须把答案需要的一切——要求、历史、资料——当场重写一遍。但我一开始想当然地以为"白板上写着就等于模型看见了"，后来发现不对：白板写得太满，字挤在一起，中间那几行它反而容易看漏。

类比边界（重要）：白板这个类比只能帮你建立"一次性、无状态、需要重写"的直觉，它至少在三处会误导你： ① 白板上所有字对人眼是等权可见的，但模型对上下文不同位置的注意强度不均匀，开头和结尾通常被利用得更好，中间偏弱 [2]； ② 白板写下后字迹是静态的，而模型读这段内容时会发生 token 之间相互影响的加权计算，内容的"含义"依赖于同窗口里还放着什么 [1]； ③ 白板不花钱，上下文要花钱——每个 token 都要计费，且长度直接影响响应速度 [5]。

2学习目标

学完这份资料后，我希望自己能够做到以下四件事（也是老师可以直接拿来考我的四条）：

  1. 说清计量关系。用自己的话解释"上下文窗口"和"token"的关系，并能对一段给定的中英文文本做出量级正确的 token 估算（不要求精确，但别差一个数量级）。
  2. 说清根源机制。讲明白自注意力如何让上下文里的 token "互相看见"，以及为什么正是这个机制，让上下文既有用、又昂贵 [1][5]。
  3. 能拆能装。列出上下文的典型组成部分（系统提示、对话历史、检索资料、工具结果），并针对一个具体任务，设计一套"该放什么、不该放什么、放在哪个位置"的组装方案。
  4. 能诊断失败。识别"中间信息丢失""上下文膨胀""会话串味"这几类典型故障，并说出至少三种应对手段（压缩、即时检索、子任务隔离等）及其适用场景 [2][3][5]。

3核心问题

下面三个问题是我读资料时真正卡住过的地方，整份资料基本就是围绕它们展开的：

  1. 既然模型能"看见"整个上下文，为什么把同一条关键证据放在第 3 段和第 30 段，模型的表现会不一样？
    直觉上"都在窗口里 = 都看得见"，但实验结论并非如此。这个问题直接指向第 4 节的"U 型曲线"。 [2]
  2. 上下文窗口从几万涨到几十万，我们解决的是什么问题，又新制造了什么问题？
    如果只是"不够装"，那扩容就够了。但扩容本身带有代价，而且有些代价不随窗口变大而消失。 [5]
  3. "提示词工程"和"上下文工程"是同一件事换了个说法吗？
    如果不是，多出来的那部分究竟是什么？这是第 4 节要素五和第 6 节的核心。 [5]

4核心机制

我把这个概念拆成五个组成要素。前三个回答"它是什么、怎么运转"，后两个回答"它为什么会失控"。

要素一：Token —— 上下文的计量单位，不是字符

模型不按"字"或"字符"来数输入，而是先把文本切成 token（分词单元），再对 token 序列做计算。所以上下文窗口的容量单位一律是 token 数。 粗略量级上：英文大约 0.75 个单词对应 1 个 token；中文由于分词器差异极大，大致可以按"1 个汉字接近 1 个 token"来估，但这只是估数量级的土办法，不同模型的分词器结果可以差出不少。

对有 Python 基础的人来说，最容易踩的坑是拿 len(text) 当 token 数：

# 错误直觉：字符数 == token 数
print(len(open("report.txt", encoding="utf-8").read()))   # 这是字符数，不是 token 数

# 只能用于"量级判断"的粗略估计，不能当真值
def rough_token_estimate(text: str) -> int:
    cn   = sum(1 for ch in text if "\u4e00" <= ch <= "\u9fff")   # 汉字
    rest = len(text) - cn
    return int(cn * 1.0 + rest * 0.25)                            # 经验系数，非精确值

# 真正准确的做法：用与该模型配套的 tokenizer 去编码
# tokens = tokenizer.encode(text); print(len(tokens))

注意：这个估算函数的意义只在于"别把 3 万字符中文档当成 3 千 token 那样轻松"，而不是给出一个可信数字。任何涉及成本或截断的判断，都应当用目标模型的真实分词器去数。

要素二：上下文窗口 —— 一块共享的、有上限的预算

上下文窗口是输入 token 与输出 token 共享的预算：你提问时送进去的内容占一部分，模型回答时生成的 token 也要从同一块额度里出。 因此"还剩多少窗口"不是固定值，而是随对话推进不断被消耗的流动资产。

另一个必须记住的性质是无状态：模型本身不会记住上一次调用。所谓"它记得我们前面聊了什么"，是因为客户端把历史消息每次都重新整包发了一遍。 

# 模型的"记忆"其实是我们每一轮都重发一遍上下文造成的错觉
messages = [
    {"role": "system", "content": "你是课程助教，只依据下面给出的资料回答，资料里没有的就说明不知道。"},
    {"role": "user",   "content": "资料：\n" + 检索到的三段 + "\n\n问题：" + 问题},
]

# 下一轮调用如果不再带上 messages，模型就完全"忘了"上一轮说过什么。
# 上下文窗口 = 这一整包 messages 编码后的 token 上限。

要素三：自注意力 —— 上下文"互相看见"的根源 [1]

这是整份资料里最关键的一环。上下文之所以有用，不只是因为信息被放进去了，而是因为 Transformer 的自注意力机制让每个 token 都能直接与其他所有 token 建立联系。 读到这里时，词与词之间不再只是"按顺序排着"，而是互相消歧、互相补充：代词靠前文确定指代，专有名词靠后文确定含义，一段报错要靠同窗口里的源码才能被读懂。

换个说法：上下文不是一堆并列摆放的纸条，而是一张每个节点都连着其他所有节点的网。这正是"上下文工程"之所以成立的前提——往窗口里加一段资料，不只是多了一条信息，而是改变了所有其他信息的解读方式。

但同一件事也是代价的来源。每个 token 都要和所有 token 配对，n 个 token 就产生 n² 量级的成对关系；上下文变长，模型捕捉这些关系的能力被摊薄，于是形成"上下文长度"与"注意力聚焦程度"之间的天然张力 [5]。
一句话记住：自注意力既是上下文的力量来源，也是它的成本来源——两者是同一个机制的两面。

需要澄清一点：n² 严格来说是计算复杂度的粗略说法（实际实现中有各种优化手段来降低算力和显存开销）。Anthropic 在文中使用它是为了说明"成对关系随长度急剧膨胀、注意力被摊薄"这一结构性张力，而不是在陈述某个具体的算法实现细节 [5]。

要素四：上下文里通常装什么

一次调用里，进入上下文的内容大致可以分成四类（外加输出格式要求）：

组成部分它负责什么典型风险
系统提示
（system prompt）		 设定角色、口吻、边界与"什么情况下该说不知道"。它是对话里最稳定、每次都会带上的那层。 写得太长、把所有边界情况都堆进去，反而会稀释真正重要的规则 [5]。
对话历史 让模型知道前面说了什么、你已经否掉了哪些方案。 失败的尝试也留在里面，会污染后续判断；无关任务的残留会"串味" [3]。
检索到的资料
（RAG）		 模型训练时没见过的内容：课程 PDF、内部文档、今天的数据。 检索回来一大堆，真正有用的那句埋在中间。
工具返回结果 命令输出、搜索结果、数据库查询结果——相当于模型从环境拿到的"真值" [4]。 一次 cat 整个目录、一次无范围的搜索，就能把窗口吃光 [3]。

注意"工具结果"这一行的性质：在智能体的循环里，工具返回不只是"答案"，更是模型下一步决策的依据。Anthropic 把"每一步从环境（工具调用结果、代码执行）获得真值"视为智能体推进的关键 [4]。而这些结果会持续累积进上下文——这就是长任务失控的起点。

要素五：位置不均匀 —— 中间信息丢失 [2]

《Lost in the Middle》这篇论文专门测了"相关信息放在上下文的什么位置"对表现的影响，任务是多文档问答和键值检索。结论是： 相关信息出现在开头或结尾时表现最好；当模型必须到长上下文的中间去取信息时，表现显著下降——即使对那些明确以长上下文为卖点的模型也是如此。 [2]

同时还有一个更一般的现象：随着上下文窗口内 token 数增加，模型从中准确回忆信息的能力会下降（这个现象被称为 context rot，直译"上下文腐烂"）。 需要强调，这不是"到某个长度突然崩掉"的断崖，而是精度逐步下滑的渐变——模型在长上下文下依然很强，只是检索精确度和长程推理的可靠性不如短上下文时 [5]。

同样是这个任务，管理之后的做法

  1. 按需取，不整包取。只让它 grep 相关符号、只读报错指向的那两三个文件，而不是 cat 整个项目——保留"路径"这类轻量引用，需要时再展开 [5]。
  2. 关键证据放两头。把 traceback 和核心源码放在资料的开头或结尾，把背景性的大段内容放中间。
  3. 把探索隔离出去。让子任务在独立的上下文窗口里做大规模搜索，只把浓缩结论（通常一两千 token）交回主对话 [5]。
  4. 该清就清。任务切换时清空上下文；同一问题纠正超过两次，说明上下文已被失败方案污染，应当清空后带着更精确的提示重新开始，而不是继续在旧上下文里打补丁 [3]。
  5. 压缩而非丢弃。接近上限时做压缩：保留架构决策、未解决的 bug、实现细节，丢掉冗余的工具输出和重复消息 [5]。

6易混淆点与边界

五条我一开始搞混、后来才想明白的地方。每条都按"常见误解 / 正确说法 / 为什么会错"拆开写。

混淆点 1：上下文窗口 ＝ 模型的记忆

常见误解"我在这个对话里教过它一次，它以后就知道了。"
正确说法上下文是一次性工作记忆，随会话结束消失。模型的持久"知识"只来自训练阶段固化进参数的东西；上下文里的内容是这次借看，不是学会了。
为什么会错因为客户端每轮都把历史消息整包重发，制造出"它记得"的错觉。你以为它在回忆，其实它每次都在重新读一遍你递给它的完整记录。换个新会话，幻觉立刻破灭。

混淆点 2：窗口够大 ＝ 把资料全塞进去最稳妥

常见误解"反正有 20 万 token 的窗口，我把 12 个源文件全贴进去，信息越全答案越准。"
正确说法装得下 ≠ 用得好。窗口变大解决了"放不下"的问题，但没有解决"用不好"的问题：token 越多，模型准确回忆其中信息的能力越弱，且中间位置的信息利用率明显偏低。好的做法是寻找最小的高信号 token 集合，而不是最大的全集 [2][5]。
为什么会错我们把"上下文窗口"类比成了硬盘或数据库——以为存进去就能无损随机读取。但它的行为更像人的工作记忆：容量有限，且注意资源会被摊薄。用一个存储系统的直觉去推断一个注意力系统的行为，自然就错了。

混淆点 3：token 数 ＝ 字符数

常见误解"这篇文档 8000 个字符，肯定装得下。"（然后被截断、或者费用远超预期）
正确说法容量单位是 token，不是字符，两者不是固定比例。中文和英文的换算比例差别尤其大，不同模型的分词器结果也不同。
为什么会错因为对我们写代码的人来说，len() 返回字符数这个直觉太根深蒂固了。加上"一个词一个 token"的粗略印象，很容易把数量级算错。凡是要判断成本、截断风险，都必须用目标模型的分词器实测。

混淆点 4：把资料放进上下文 ＝ 模型学会/相信了这份资料

常见误解"我把课程 PDF 塞进去了，它现在以这份 PDF 为准，不会再用训练时的旧知识了。"
正确说法上下文内容只是影响这次输出的条件，不会覆盖训练所得。当上下文资料与模型原有认知冲突时，它未必优先采信上下文。这也是为什么系统提示里要明确写"只依据给定资料回答，没有就说不知道"——靠显式约束，而不是靠"塞进去"这个动作本身。
为什么会错把"提供条件"误当成了"更新参数"。混淆了推理时的上下文与训练时的权重更新——这是两个完全不同的机制，前者是临时的、逐次调用的，后者才是持久的。

混淆点 5：压缩上下文 ＝ 无损操作

常见误解"上下文快满了就让它自动压缩一下，反正信息都还在。"
正确说法压缩是有损的取舍。它的标准做法是保留架构决策、未解决的 bug 和实现细节，丢弃冗余的工具输出和重复消息。被丢掉的东西不会回来——所以才有"在压缩指令里明确要求保留哪些内容"这一说 [3][5]。
为什么会错"压缩"这个词是从数据工程借来的，让人联想到无损压缩。但这里的压缩是摘要，是模型在判断"什么重要"——判断错了就会永久丢信息。

边界：什么时候"上下文"这个词根本不是我说的前面那个意思

提醒自己一个命名陷阱：Anthropic 的 Model Context Protocol（MCP） 名字里也有 "Context"，但它是用于工具集成的协议，和"上下文窗口"不是一个概念 [4]。 看文档时遇到 "context" 要先判断它指的是模型这次能看见的 token 集合，还是系统集成层面的某种协议或机制。

7自测题

共 5 题，其中第 1 题是陷阱判断题。建议先写在纸上再对照答案。

第 1 题（判断题 · 陷阱题）："某模型的上下文窗口是 200K token。因此，我把项目的全部 12 个源文件一次性贴进对话，模型就能充分利用每一个文件的每一处细节，这是最稳妥的做法。"

错误这句话把"装得下"直接等同于"用得好"了，有两个独立的问题。

  • 问题一（位置）。即使全部内容都在窗口内，模型对不同位置信息的利用程度也不均匀。实验表明相关信息在开头或结尾时表现最好，在中间时显著退化，连以长上下文为卖点的模型也不例外 [2]。你把 12 个文件平铺进去，就等于把大部分信息放进了"中间"这个低效区。
  • 问题二（密度）。随着上下文 token 数增加，模型准确回忆其中信息的能力会下降；好的做法是找最小的高信号 token 集合，而不是最大的全集 [5]。

更稳妥的做法：先用 grep 之类的手段定位相关范围，只把命中的片段送进去，并把最关键的那段放在开头或结尾。

这题的陷阱在于它说的事实都没错（窗口确实有 200K、确实装得下），错在从"装得下"跳到了"充分利用"。这类"前提都对、结论跳跃"的判断题最容易骗人。

第 2 题（简答）：请用一句话说清"自注意力"与"上下文窗口"的关系——为什么上下文既能让模型变聪明，又会让模型变贵？

参考要点因为它们是同一个机制的两面：

  • 让它变聪明：自注意力让上下文里每个 token 都能与其他所有 token 建立联系，词与词互相消歧、互相补充，所以放进来的资料能被真正"读懂"，而不是孤立地摆着 [1]。
  • 让它变贵：每个 token 都要和所有 token 配对，n 个 token 产生约 n² 量级的成对关系；长度增加时，模型捕捉这些关系的能力被摊薄，注意力聚焦度下降，同时算力和计费成本也在上升 [5]。

答到"互相建立联系"＋"n² 摊薄/成本上升"两点，且明确指出二者同源，就算过关。

第 3 题（辨析）：我把一份 2026 年的课程讲义放进上下文，让模型据此答题。请问：模型现在"学会"这份讲义了吗？如果讲义内容和它训练时的旧说法冲突，它会一定采信讲义吗？

参考答案两个问题都是否定的。

  • 没有"学会"。上下文内容只是本次推理的条件，会话结束即消失。真正的"学会"要发生在训练阶段、固化进模型参数，与把文本放进上下文是完全不同的机制。
  • 不保证采信。当上下文资料与模型原有认知冲突时，模型未必优先采信上下文。要让它以给定资料为准，必须在系统提示里显式约束（例如"只依据给定资料回答，资料中没有的就说明不知道"），而不能指望"塞进去"这个动作自动生效。
第 4 题（估算）：一篇约 6000 个汉字的中文实验报告，按文中给出的粗略量级，它大概占多少 token？你打算怎么验证这个估算靠不靠谱？

参考答案

  • 估算：按"1 个汉字接近 1 个 token"的粗口径，约 6000 token 上下。如果这个数量级对你很重要（比如要判断是否会超窗口、要算成本），这个精度是不够的。
  • 怎么验证：用目标模型配套的分词器实际编码一遍，取 len(tokens)。中文的分词器差异很大，跨模型套用估算值会失真。
  • 另一个容易漏的点：别忘了输出也要占同一块额度。输入 6000 token 不代表还剩"窗口容量 − 6000"全部可用，模型的回答还要从里面出。

本题的评分点不在数字本身（估算偏差是被允许的），而在于你是否知道"字符数 ≠ token 数"，以及是否知道必须用真实分词器验证。

第 5 题（设计）：你在用 AI 助手改一个课程项目。改到第四轮时，它开始在同一个地方反复出错，你已经纠正了三次。请说出至少两种应对手段，并说明各自适合什么情况。

参考要点任选以下三种中的两种即可，关键是说清适用场景：

  • 清空重来。同一问题纠正超过两次，说明上下文已被失败的尝试污染；此时应当清空上下文，带着一个吸收了前几轮教训的、更精确的提示重新开始。一个干净的新会话配一个好提示，通常胜过一段堆满纠正记录的长会话 [3]。
    适合：方向性错误、早期就跑偏的会话。
  • 压缩（compaction）。把接近上限的对话做摘要，保留架构决策、未解决的 bug 和实现细节，丢掉冗余的工具输出和重复消息，然后用摘要开启新上下文 [5]。
    适合：需要保留大量来回讨论的连续任务；压缩时可以显式指定"必须保留什么"。
  • 子任务隔离。把大规模探索放进独立的上下文窗口，只让浓缩后的结论回到主对话 [5]。
    适合：需要读大量文件、但主任务只需要结论的调研型工作。

加分点：提到"任务切换时清空上下文，避免无关内容串味" [3]。

9我的疑问

写完这份资料后，以下三个问题我仍然没有搞懂，希望能在课堂上问老师或继续查：

  1. "中间信息丢失"的机理到底是什么？ 《Lost in the Middle》令人信服地报告了现象（开头/结尾好、中间差），但我没能在论文里读到一个确定的因果解释：这究竟源于位置编码的特性、注意力权重在长序列上被稀释、还是训练数据中"关键信息恰好在中间"的样本本来就少？ 如果机理未定，那我把关键内容"挪到开头"这个做法，就只是对现象的经验性规避，而不是对症下药——下次模型架构一变，这个技巧还灵不灵？ [2]
  2. "n² 成对关系"和"注意力预算被耗尽"，是同一件事吗？ Anthropic 的文章用 n² 来解释注意力为何被摊薄 [5]，但我有点困惑：n² 描述的是计算规模，而"注意力被摊薄"描述的是模型行为。 现在有各种工程手段（如更高效的注意力实现）显著降低了长序列的算力和显存开销——那么，它们究竟有没有同时改善"模型对长上下文的利用质量"，还是仅仅让长上下文跑得更快、但照样看漏中间？如果是后者，那"算力成本"和"质量衰减"这两件事就应该被分开讨论，而我在第 4 节把它们写在了一起。
  3. 各家公布的"上下文窗口"数字，口径一致吗？ 厂商宣传的"200K 上下文"到底指什么：是输入上限，还是输入输出之和？它统计的是模型的原生分词结果，还是某个换算后的"约等于 X 页文档"？ 如果口径不统一，那么"模型 A 的窗口比模型 B 大一倍"这类比较本身可能就没有意义。我在第 4 节要素二写"输入输出共享预算"，但我不确定这对所有厂商都成立。

第 2 条和第 3 条其实指向同一个担忧：我在学习过程中可能把"厂商文章里的解释性说法"当成了"有定论的技术事实"。这也是我写第 8 节那两条说明的原因。
